# Generated types

Your content model is TypeScript, and so is everything derived from it. The CLI
turns `app/content-objects/` into types your editor and your build understand.

## What is generated

| artifact | where | what it is |
|---|---|---|
| **types declaration** | `app/generated/tangen-types.d.ts` | an interface per content type, per global and per custom table, plus the registry augmentation |
| **content tables** | `app/generated/content-tables.ts` | the drizzle table objects, for your own code and the types. The server builds its runtime tables from the registry of its database, so this file never decides what a process reads |
| **custom tables** | `custom-tables.ts`, when you have any | the same, for `customTables` |

## When it happens

| command | regenerates |
|---|---|
| `tangen push` | all of it, **after** the schema is applied |
| `tangen types` | the types declaration only |
| `tangen schema` | the generated registry |

`push` writes the files in its final step, after the DDL has committed. So the
generated files always describe a schema that actually exists - they are never
ahead of the database.

## What you get

```ts app/generated/tangen-types.d.ts
// DO NOT EDIT - generated by `tangen types`

export interface TangenSystemFields {
  id: string
  title: string | null
  slug: string | null
  status: 'draft' | 'published' | 'archived'
  publishedAt: string | null
  scheduledAt: string | null
  createdAt: string
  updatedAt: string
  createdBy: string | null
  updatedBy: string | null
}

/** Content type "article" (Article) */
export interface Article extends TangenSystemFields {
  subtitle?: string | null
  body?: string | null
}
```

Every content type extends `TangenSystemFields`, so `id`, `slug`, `status` and
the timestamps are always there without you declaring them.

## Why your queries are typed without generics

The file ends with a **module augmentation** against `@tangen/types`:

```ts
declare module '@tangen/types' {
  interface TangenRegistry {
    content: TangenContentTypes
    globals: TangenGlobals
    tables: TangenTables
    locales: 'en' | 'fr' | 'de'
    roles: 'owner' | 'admin' | 'editor' | 'viewer'
    extensions: 'forms' | 'seo'
  }
}
```

That is what makes this work with no generic parameter:

```ts
const { data } = await tangen.objects('article').limit(10).get()
//                                    ^ a literal union - a typo is a compile error
//      ^ data is Article[]
```

It also types `globals('site_settings')`, custom tables, locale codes and role
names. **You never write `objects<Article>('article')`** - if an example shows
that, it is out of date.

## When to regenerate

Any time the model changes:

- a field added, renamed, retyped or removed
- a content type added or removed
- a global, a custom table, a locale or a role added
- a workspace's extensions changed

`tangen push` does it for you. Run `tangen types` on its own when you have
changed the model but are not ready to touch the database - your editor catches
up without a schema change.

**If your editor disagrees with your schema file, you have not regenerated.**
That is almost always the cause.

## Do not edit generated files

They carry a `DO NOT EDIT` header and the next push overwrites them. Commit
them - your build and your CI need them - but change them only by changing the
model.
